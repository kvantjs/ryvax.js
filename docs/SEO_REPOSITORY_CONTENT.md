Ryvax.js is a React-first full-stack TypeScript framework for SaaS products, APIs, internal platforms, documentation systems, and applications that need a consistent frontend, backend, and operations boundary.

It combines file-based routing, React server-side rendering (SSR), static-site generation (SSG), hydration, streaming, typed API contracts, authentication primitives, cache and job interfaces, health checks, observability hooks, and portable Node.js deployment.

> Ryvax keeps runtime behavior explicit and provider-neutral. The framework does not require a proprietary hosting platform.

- **Current version:** `2.3.4`
- **Package:** [`@kvantjs/ryvax.js`](https://www.npmjs.com/package/@kvantjs/ryvax.js)
- **Documentation:** [Ryvax documentation](https://kvantjs.github.io/ryvax.js/)
- **License:** [MIT](./LICENSE)
- **Node.js:** `>=20`

## Why Ryvax.js?

Modern full-stack applications often need more than a UI renderer. They need predictable route discovery, server rendering, API behavior, request cancellation, bounded input, background work, cache semantics, deployment artifacts, and operational diagnostics.

Ryvax provides these contracts in one TypeScript-oriented framework while keeping external providers replaceable. Database, cache, queue, storage, metrics, identity, AI, and deployment integrations are modeled through explicit interfaces instead of being mandatory runtime dependencies.

## Features

### Application and routing

- File-based routing through `pages/` with support for dynamic segments and catch-all routes.
- App Router conventions through `app/`, including `page.tsx`, `route.ts`, `layout.tsx`, loading states, error boundaries, and route groups.
- Deterministic route manifests generated by the compiler.
- Typed request context with parameters, query strings, headers, body, abort signals, environment values, and runtime information.

### Rendering and frontend

- React 19 rendering with SSR, SSG, hydration, and HTML streaming.
- Static export for CDN-oriented sites.
- Client navigation primitives through `@kvantjs/ryvax.js/client`.
- Server actions with stable build-time identifiers and bounded, origin-checked transport.
- Experimental React Server Components track with an explicit compatibility boundary.

### APIs and HTTP

- TypeScript API handlers with named HTTP method exports.
- JSON, body, redirect, stream, `OPTIONS`, and safe `HEAD` response behavior.
- Request deadlines, abort propagation, bounded request bodies, and stable malformed-JSON errors.
- Middleware composition and validation contracts.

### Platform contracts

- Authentication, signed sessions, CSRF validation, authorization, and rate limiting primitives.
- Process-local response cache with TTL, stale-while-revalidate, tags, invalidation, and miss deduplication.
- Provider-neutral data cache, database, storage, metrics, and job queue interfaces.
- Health and readiness checks with structured reports and HTTP `503` behavior for unhealthy results.
- Structured logs, request IDs, metrics hooks, audit events, resilience utilities, and request tracing.

### Developer experience

- `defineConfig()` for typed framework configuration.
- `ryvax generate` for deterministic route and configuration declarations.
- Optional TypeScript Server Plugin for route-aware diagnostics and completion.
- `ryvax doctor`, `ryvax routes`, `ryvax inspect`, `ryvax analyze`, and `ryvax benchmark` for project diagnostics and build inspection.
- Scaffolding through `create-ryvax-app` and ready-to-run React, SaaS, documentation, and API documentation templates.

### Deployment

- Portable Node.js deployment output.
- Vercel Build Output API adapter.
- Netlify Node Function adapter.
- Docker deployment output.
- Edge adapter primitives with explicit runtime boundaries.
- No claim of persistent filesystem, WebSocket durability, or universal serverless behavior: those properties depend on the deployment platform and application architecture.

## Architecture

```text
Application source
  pages/ or app/
        |
        v
Route discovery and compiler
  route classification, boundaries, actions
        |
        v
Normalized build manifest
  routes, bundles, assets, client entry
        |
        +--------------------+
        |                    |
        v                    v
Node runtime            Static export
SSR, APIs, streams      CDN-ready pages/assets
        |
        v
Deployment adapters
Node, Docker, Vercel, Netlify, Edge boundary
```

The runtime owns request lifecycle behavior, route matching, rendering, API dispatch, headers, cancellation, and error handling. The application owns data policy, provider configuration, secrets, retention, authorization policy, and production capacity planning.

## Technology stack

- **Language:** TypeScript.
- **UI:** React 19 and React DOM.
- **Runtime:** Node.js 20 or newer.
- **Build:** esbuild with an adaptive build path and experimental alternative backend support.

## Quick start

Create a route at `pages/index.tsx`:

```tsx
export default function HomePage() {
  return (
    <main>
      <h1>Ryvax.js</h1>
      <p>Full-stack TypeScript applications with explicit runtime contracts.</p>
    </main>
  );
}
```

Create a typed API route at `pages/api/health.ts`:

```ts
import type { ApiHandler } from '@kvantjs/ryvax.js';

export const GET: ApiHandler = async ({ signal }) => {
  await checkDependency({ signal });
  return { json: { ok: true } };
};
```

Configure the application in `framework.config.ts`:

```ts
import { defineConfig } from '@kvantjs/ryvax.js';

export default defineConfig({
  poweredBy: false,
  observability: {
    requestId: true,
    requestLogging: false
  },
  limits: {
    bodyBytes: 2 * 1024 * 1024,
    requestTimeoutMs: 60_000
  }
});
```

Run the development server:

```bash
npm run dev
```

## CLI reference

| Command | Purpose |
| --- | --- |
| `ryvax create <name>` | Creates a React TypeScript application. |
| `ryvax dev --port 3000` | Starts development mode with watching and HMR. |
| `ryvax build` | Builds production route bundles and static output. |
| `ryvax start --port 3000` | Starts a production manifest. |
| `ryvax export --out-dir dist` | Exports static pages and assets. |
| `ryvax deploy --out-dir dist` | Creates a portable Node deployment package. |
| `ryvax build:vercel` | Emits Vercel Build Output API artifacts. |
| `ryvax build:netlify` | Emits a Netlify Node Function deployment. |
| `ryvax build:docker` | Emits Docker-oriented deployment output. |
| `ryvax generate` | Generates `.ryvax/routes.d.ts` and `.ryvax/config.d.ts`. |
| `ryvax doctor --json` | Reports environment and manifest diagnostics. |
| `ryvax routes --json` | Prints a scriptable route projection. |
| `ryvax inspect --json` | Prints the project graph and diagnostics. |
| `ryvax analyze --json` | Reports bundle sizes and build diagnostics. |
| `ryvax benchmark --json` | Reports deterministic build metrics. |

Use separate `--out-dir` values when running concurrent builds.

## TypeScript and IDE integration

Ryvax can use an optional TypeScript Server Plugin for route-aware development tooling. Add it to `tsconfig.json`:

```json
{
  "compilerOptions": {
    "plugins": [
      { "name": "@kvantjs/ryvax.js/typescript-plugin" }
    ]
  }
}
```

The plugin is a development-time enhancement. It must not be required by the runtime. For CI, `tsc`, and editors that do not load TypeScript plugins, generate declarations explicitly:

```bash
npx ryvax generate
```

Generated files are artifacts and should not be edited manually.

## Production and deployment

Build and run the portable Node artifact:

```bash
npm run build
npm run deploy
PORT=8080 node dist/server.mjs
```

Vercel and Netlify output:

```bash
npx ryvax build:vercel
npx ryvax build:netlify
```

Static export is appropriate for pages that do not require server rendering, API execution, streaming, or runtime-only dynamic data:

```bash
npx ryvax export --out-dir dist
```

For multiple instances, use a distributed cache and durable queue. Do not treat process-local memory, temporary filesystems, or a serverless function as durable infrastructure.

### Passo 1 — Publicar uma página técnica canônica

Mantenha o README como a página de entrada do projeto e use a documentação para aprofundar conceitos. ### Passo 2 — Criar um artigo técnico no Dev.to

Publique um tutorial reproduzível, por exemplo: **“Building a typed API with file-based routing in Ryvax.js”**. Mostre o código mínimo, explique a decisão arquitetural e inclua links para a documentação e o repositório. Use uma canonical URL quando o conteúdo também existir no domínio oficial. ### Passo 3 — Divulgar uma demonstração no LinkedIn

Publique um vídeo curto ou GIF que mostre o fluxo `create → dev → build → deploy`. Explique qual problema foi resolvido e inclua uma única chamada para ação: testar o starter ou ler o quickstart. Use termos naturais como “framework full-stack TypeScript”, “React SSR” e “file-based routing”, sem repetir palavras-chave artificialmente.

### Passo 4 — Participar de comunidades com contexto real

Compartilhe o projeto em comunidades relevantes, como Reddit e fóruns de TypeScript, apenas quando houver uma pergunta ou discussão compatível. Escreva um post técnico com limitações explícitas, resultados reproduzíveis e instruções para teste. Responda comentários com links para a seção exata da documentação, em vez de publicar mensagens promocionais repetidas.
